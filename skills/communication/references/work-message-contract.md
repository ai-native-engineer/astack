# Work Message Contract

Use this reference before drafting, rewriting, sending, or editing outbound work messages.

## Before Writing

Identify these privately:

- Reader: who needs to decide, act, or understand?
- Purpose: inform, request, decide, unblock, hand off, correct, persuade, or archive.
- Desired output: the exact choice, action, status, or decision wanted after reading.
- Constraint: urgency or timing flexibility, deadline, owner, file/link, risk, unknown, security boundary, or fallback.

If a missing item changes the work, ask or state it as `확인 필요:`. Do not hide uncertainty behind polite wording.

## Default Shape

- Put the conclusion, request, or handoff purpose in the first visible line.
- Simple message order: point -> necessary context -> next action.
- Request order: what -> why -> how -> when.
- Decision-support order: point -> reason -> evidence/example -> action.
- Do not send a standalone greeting. Put the greeting and purpose in the same message.
- Use concrete facts: dates, counts, file names, channel names, ticket IDs, parameters, links.
- If the message is more than a few lines, use short section labels and bullets.
- Simple does not always mean short. Include enough detail to prevent follow-up churn, but chunk it by channel conventions.

## Clarity Checks

- Reader fit: write for the recipient's job, not for the sender's research trail.
- First 5 seconds: a busy reader should understand why they got the message and what to do.
- 3W1H: for requests, include `왜`, `무엇을`, `어떻게`, `언제까지`.
- Timing: state whether the request is urgent, deadline-bound, or flexible when that changes prioritization.
- Separation: do not mix facts, requests, opinions, and feelings in the same sentence.
- Evidence: support important judgments with a number, example, file, link, or observed event.
- Language: use correct spelling and minimize abbreviations, slang, and unexplained jargon. Define a necessary term once.
- Unknowns: say what is not confirmed, how it will be checked, and by when.
- Action filter: remove background that does not change the recipient's action.
- Visual aid: use a flowchart, image, GIF, or video only when it communicates the information faster than text.

## Proposal / Persuasion Lens

Use this only for sales, approval, stakeholder buy-in, proposal, or "why us" messages.

- Start from the recipient/customer's pain, decision criteria, and language. Do not start from our features.
- Check the field information before writing: measurable value, pain point, decision-maker, decision criteria, hidden constraint or budget, alternatives, and competitors.
- Write a one-sentence win theme: customer pain -> our differentiated strength -> expected outcome.
- Avoid the death triangle: shallow pain analysis, feature bragging, and insufficient field information.
- If there is an alternative or competitor, neutralize it by explaining why that strength is not the deciding factor for this recipient.
- Use `OREO` when the point must be sharp: opinion -> reason -> example -> opinion.
- Use `STAR` when explaining an achievement or case: situation -> task -> action -> result.
- Convert `YES, BUT` into `YES, IF` when the goal is to keep momentum while naming a condition.

## Tone

- Korean polite register by default, but keep judgment clear.
- Use a middle-temperature work tone: direct, practical, not cold, not flattering.
- Default endings: `~입니다`, `~로 보면 됩니다`, `~가 핵심입니다`, `~해주세요`, `~로 진행하면 됩니다`, `~로 정리했습니다`.
- Use `~것 같습니다` only for real uncertainty, open suggestions, or assumptions that still need confirmation.
- Do not stack `~것 같습니다` across multiple sentences. It reads like the sender is avoiding a decision.
- Make requests direct but not rude: `확인해주세요`, `먼저 봐주세요`, `이 기준으로 진행해주세요`.
- Remove defensive fillers: `제 생각엔`, `개인적으로`, `어쩌면`.
- Keep it colleague-to-colleague: practical, specific, low on praise and decoration.

## Formatting

- Prefer compact bullets or numbered lists for operational handoffs.
- Use numbered lists for multiple items and letters such as A, B, C for mutually exclusive choices.
- Prefer plain section labels such as `전제`, `핵심 판단`, `체크할 포인트`, `요청`, `막히면`.
- For compact comparisons, use `항목: 내용` or short numbered sections.
- Use backticks for file paths, parameters, functions, commands, and literal labels.
- Avoid fragile formatting if the delivery channel may render it poorly.

## Avoid

- Over-thanking or empty praise: `정말 감사합니다`, `대단하세요`.
- Exclamation-heavy copy.
- Decorative emoji in message copy unless the user already uses it or explicitly asks. Channel-native status reactions follow the selected channel overlay.
- Em dash-heavy writing; use commas or line breaks.
- Vague intensifiers: `근본적으로`, `본질적으로`, `매우`, unless backed by concrete detail.
- Rewriting a previously approved body just because you are sending or editing it.
- Assistant-like framing: `정리해드리면`, `도움이 되셨으면`, `좋은 하루 되세요`.

## Edit Discipline

When editing an existing message:

- First identify what must change: length, structure, facts, tone, typo, attachment, mention, or placement.
- Keep approved wording stable outside that scope.
- If replacing a long message with a compact version, remove or update duplicate follow-ups when the channel supports it.
- After sending/editing, verify the posted message when the channel tooling supports verification.
- If the posted output has broken formatting, edit in place with simpler plain-text structure instead of adding a new corrective reply.
